# 10 высокоэффективных практик Claude Code (и 5 антипаттернов)

Claude Code — это не просто умное автодополнение. При правильном использовании это множитель усилий, который может поднять производительность одного разработчика до уровня небольшой команды. При неправильном — дорогостоящее отвлечение, порождающее посредственный код, который потом приходится исправлять самому.

Это руководство собирает самые высокоэффективные практики — те, что реально меняют то, что Claude может сделать для вас, — вместе с антипаттернами, которые мы чаще всего наблюдаем при первом внедрении в командах.

---

## 10 практик

### 1. Используйте CLAUDE.md для передачи Claude постоянного контекста о кодовой базе

У Claude нет памяти между сессиями. Каждый разговор начинается с нуля. Без файла `CLAUDE.md` вы тратите первые 10 минут каждой сессии на повторное объяснение своего стека, соглашений и ограничений.

Файл `CLAUDE.md` в корне проекта загружается автоматически в начале каждой сессии Claude Code. Это самое значимое, что вы можете сделать.

Хороший `CLAUDE.md` включает:

- **Технологический стек** — языки, фреймворки, версии рантаймов
- **Структура проекта** — что находится в каких директориях и почему
- **Команды разработки** — как запускать тесты, линтер, сборку, dev-сервер
- **Соглашения о коде** — паттерны именования, стиль обработки ошибок, порядок импортов
- **Запретные файлы** — «никогда не изменяйте `db/schema.prisma` напрямую»
- **Предметная лексика** — бизнес-термины, которые Claude должен использовать последовательно

```markdown
# My Project — Claude Context

## Stack
- Next.js 15, TypeScript strict mode, Tailwind CSS
- Postgres via Drizzle ORM
- Vitest for unit tests, Playwright for E2E

## Commands
- `pnpm dev` — start dev server on :3000
- `pnpm test` — run all tests
- `pnpm lint` — ESLint + Prettier check

## Conventions
- All API routes live in `src/app/api/`
- Database queries go through `src/lib/db/` — never query directly from components
- Use `Result<T, E>` pattern for error handling, not try/catch in business logic

## Never touch
- `src/generated/` — auto-generated, will be overwritten
```

Держите его в пределах 300 строк. CLAUDE.md, на чтение которого уходит 15 минут, побеждает свою собственную цель.

### 2. Используйте параллельных агентов для независимых задач

Claude Code поддерживает запуск нескольких агентов одновременно. Когда у вас есть задачи, которые не делят состояние — «написать юнит-тесты для модуля A» и «обновить API-документацию для модуля B» — параллельный запуск сокращает стеновое время вдвое или больше.

Навык `/dispatching-parallel-agents` (или явная просьба Claude) запустит сабагентов в отдельных worktrees, выполнит задачи параллельно и объединит результаты. Особенно эффективно для:

- Параллельного написания тестов для нескольких модулей
- Запуска проверки безопасности одновременно с написанием feature-кода
- Перевода документации на несколько языков сразу
- Независимого исследования в нескольких кодовых базах

Ограничение: параллельные агенты не могут безопасно делить изменяемое состояние. Если два агента пишут в один файл, возникнут конфликты. Формулируйте задачи так, чтобы каждый агент владел отдельным набором файлов.

---

### 3. Используйте worktrees для изолированной работы над фичами

`git worktree` позволяет одновременно иметь несколько веток одного репозитория в отдельных директориях — без stash, без переключения веток, без смешения контекстов.

Claude Code нативно интегрируется с worktrees. Когда вы начинаете работу над фичей, создайте выделенный worktree:

```bash
git worktree add ../my-feature-worktree -b feature/new-dashboard
```

Каждый worktree получает собственную сессию Claude Code. Преимущества:

- **Нет загрязнения** — изменения в одной фиче не затронут другую случайно
- **Параллельная разработка** — две фичи, два агента, одновременно
- **Лёгкая очистка** — `git worktree remove ../my-feature-worktree` по завершении
- **Безопасные эксперименты** — попробуйте рискованный рефакторинг в worktree; если что-то пойдёт не так, просто удалите его

Особенно ценно, когда Claude выполняет длинный многошаговый план. Если что-то пойдёт не так, основное рабочее дерево останется нетронутым.

### 4. Пишите точные, ограниченные промпты — не размытые запросы

Качество вывода Claude напрямую пропорционально качеству вашего промпта. Размытые запросы порождают размытую работу.

**Слабый промпт:**
> «Почини аутентификацию»

**Сильный промпт:**
> «Логика обновления JWT-токена в `src/lib/auth/refresh.ts` молча ломается при истёкшем токене — возвращает null вместо исключения. Обнови её так, чтобы она выбрасывала `AuthError` с кодом `TOKEN_EXPIRED`. Обнови вызывающий код в `src/app/api/auth/route.ts` для обработки этой ошибки с возвратом 401 и `{ error: 'token_expired' }`. Добавь тест в `src/lib/auth/refresh.test.ts`, покрывающий случай с истёкшим токеном.»

Второй промпт говорит Claude точно, что сломано, где находится, как выглядит исправление и что должен покрывать тест. Claude может его выполнить без угадывания.

Три правила ограниченных промптов:
1. **Называйте файлы** — не говорите «модуль auth», а `src/lib/auth/refresh.ts`
2. **Определяйте критерии приёмки** — как выглядит «готово»?
3. **Указывайте ограничения** — «не меняй публичный API», «без новых зависимостей»

### 5. Давайте Claude использовать режим планирования для сложной многошаговой работы

Для задач, затрагивающих более трёх-четырёх файлов, или задач, где правильный подход неочевиден, попросите Claude **сначала спланировать**.

> «Прежде чем писать код, составь пошаговый план реализации миграции пользовательской аутентификации с JWT на сессионные токены. Перечисли каждый файл, который изменится, что именно изменится и порядок операций.»

Проверьте план. Исправьте любые недопонимания. Только потом скажите «выполняй план».

Это позволяет рано выявить два вида провала:
- **Неверное понимание объёма** — Claude планирует изменить 15 файлов, а вы имели в виду 3
- **Ошибки порядка операций** — Claude собирался мигрировать базу до обновления слоя ORM

Режим планирования добавляет 2 минуты вначале и экономит 30 минут на откатах.

### 6. Используйте навыки для повторяющихся рабочих процессов

Если вы выполняете один и тот же тип задачи более двух раз в неделю, её место — в файле навыка. Навыки — это переиспользуемые процедурные шаблоны, хранящиеся в `~/.claude/plugins/` или `.claude/plugins/`.

Перспективные кандидаты для навыков:
- **Код-ревью** — ваш специфичный чек-лист команды, не универсальный
- **Миграция базы данных** — проверки безопасности до и после
- **Чек-лист деплоя** — 8 вещей, которые вы всегда проверяете перед выкаткой
- **Реагирование на инцидент** — структурированные шаги триажа, когда всё горит
- **Онбординг** — пошаговая настройка для нового инженера

Каждый раз, когда вы замечаете, что даёте Claude одни и те же многошаговые инструкции, это навык в ожидании написания. Инвестиция в 20 минут на файл навыка окупается в течение недели.

### 7. Настройте хуки для автоматических проверок качества

Claude Code поддерживает хуки — команды оболочки, которые автоматически запускаются при определённых событиях жизненного цикла: до вызова инструмента, после него, при запуске сессии, при её завершении.

Хуки обеспечивают соблюдение стандартов качества без необходимости помнить о них. Распространённые применения:

**Пре-коммит хук** (запускается перед каждым git-коммитом Claude):
```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "if echo \"$CLAUDE_TOOL_INPUT\" | grep -q 'git commit'; then npm test && npm run lint; fi"
          }
        ]
      }
    ]
  }
}
```

**Пост-запись хук** (запускается после того, как Claude записал файл):
```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write",
        "hooks": [
          {
            "type": "command",
            "command": "npx prettier --write \"$CLAUDE_TOOL_RESULT_PATH\" 2>/dev/null || true"
          }
        ]
      }
    ]
  }
}
```

Хуки превращают Claude Code из инструмента запрос-ответ в систему разработки с принуждением к качеству.

### 8. Используйте /compact для управления контекстным окном

Каждое сообщение в обмене с Claude потребляет пространство контекстного окна. Длинные сессии — особенно те, что включают чтение множества файлов — в конечном итоге вытесняют более ранний контекст из окна. Когда это происходит, Claude теряет осведомлённость о решениях, принятых ранее в сессии.

Команда `/compact` сжимает текущую сессию в компактное представление и продолжает с него. Запускайте её:

- После завершения крупного этапа работы («мы закончили слой аутентификации, теперь начинаем UI»)
- Когда вы замечаете, что Claude повторяет уже сделанную работу
- Перед началом новой подзадачи, которой нужен свежий контекст

Думайте о `/compact` как о «сохранить и сделать чекпойнт» — особенно полезно в сессиях, которые длятся часами или охватывают несколько фич.

### 9. Коммитьте часто, чтобы Claude мог видеть историю git

Claude Code читает историю git, когда ему нужно понять, как развивалась кодовая база. `git log`, `git blame` и `git diff` — одни из наиболее используемых им инструментов исследования.

Редкая история коммитов — огромные коммиты с сообщениями «wip» или «updates» — затрудняет исследование Claude. Насыщенная, хорошо описанная история делает его лучше:

```
feat(auth): add JWT refresh endpoint
fix(auth): handle expired refresh tokens with TOKEN_EXPIRED error
test(auth): add coverage for expired and invalid refresh tokens
refactor(auth): extract token validation to lib/auth/validate.ts
```

Когда Claude нужно понять, почему существует тот или иной фрагмент кода, чёткая история git позволяет отследить логику рассуждений. Без неё Claude вынужден угадывать — и иногда угадывает неверно.

Это также помогает Claude генерировать точные сообщения коммитов, поскольку он может воспроизводить соглашения вашей команды по примерам.

---

### 10. Используйте инструменты задач для отслеживания прогресса в длинных сессиях

Для работы, охватывающей несколько часов или сессий, используйте интеграцию с отслеживанием задач в Claude Code:

```bash
task-hub create "Migrate user auth to sessions" --agent Claude
```

В конце сессии обновите задачу:

```bash
task-hub touch auth-migration --status in-progress --next "implement session store in Redis"
```

В начале следующей сессии Claude может прочитать состояние задачи и продолжить с того места, где остановился — без повторных объяснений. Это также создаёт лёгкий журнал аудита сделанного, что полезно для код-ревью и ретроспектив.

Для больших проектов сочетание отслеживания задач с `CLAUDE.md`, ссылающимся на хаб задач, даёт Claude всё необходимое для быстрой ориентации.

## 5 антипаттернов

### Антипаттерн 1: Передача Claude огромных контекстных дампов без структуры

Вставить 3000 строк кода в промпт и спросить «что здесь не так?» — наименее эффективный способ использовать Claude Code. Модель должна сначала разобраться, что здесь релевантно, прежде чем приступить к вашему реальному вопросу.

**Решение:** Давайте Claude целевой контекст. Указывайте конкретные файлы через `Read`. Задавайте ограниченный вопрос. Если проблемное пространство велико, попросите Claude провести исследование самостоятельно — он систематически прочитает нужные файлы, что эффективнее вашего предварительного отбора.

---

### Антипаттерн 2: Подтверждение каждого запроса разрешений без чтения

Claude Code запрашивает разрешение перед запуском команд, записью файлов или сетевыми запросами. Эти запросы существуют по причине. Разработчики, машинально нажимающие «разрешить», регулярно обнаруживают, что Claude собирался запустить `rm -rf` на чём-то важном, или закоммитить учётные данные, или записать в неверное окружение.

**Решение:** Читайте запросы разрешений. Когда Claude собирается запустить команду Bash, команда показана. Взгляните на неё. Проверка, занимающая 2 секунды, уберегла многих инженеров от дорогостоящих ошибок.

---

### Антипаттерн 3: Никогда не использовать CLAUDE.md (у Claude нет памяти проекта)

У Claude нет постоянной памяти. Каждая сессия начинается с нуля. Без CLAUDE.md вы либо постоянно повторно объясняете свой проект (потеря времени), либо Claude делает предположения, не соответствующие вашей кодовой базе (потеря усилий на исправление ошибок).

**Решение:** Напишите CLAUDE.md сегодня. Это занимает 30 минут и окупается в каждой последующей сессии. Смотрите практику №1 выше.

---

### Антипаттерн 4: Просить Claude сделать всё за один раз

«Создай полностек-платформу электронной коммерции с аутентификацией, платежами, инвентарём и административной панелью» — это не промпт, это техническое задание. Claude попытается это сделать, что-то создаст, и это окажется неверным в местах, которые дорого исправлять, поскольку промежуточные результаты не проверялись.

**Решение:** Декомпозируйте. Разбивайте большие запросы на фазы. Проверяйте результат на каждой фазе. Исправляйте перед продолжением. Claude исключительно хорош в длительной сфокусированной работе над чётко определённой задачей; с неограниченным объёмом он менее надёжен.

---

### Антипаттерн 5: Игнорирование вывода инструментов перед подтверждением успеха

Claude Code — это агентная система: она запускает инструменты и интерпретирует их вывод. Но интерпретация Claude вывода инструментов не всегда верна. Тесты могут пройти по неправильной причине. Линтер может сообщать о предупреждениях, которые при беглом чтении выглядят как успех. Деплои могут успешно завершиться в CI, но упасть в продакшене.

**Решение:** Когда Claude говорит «все тесты прошли» или «деплой успешен», проверяйте фактический вывод, на котором он основывает это заключение. Попросите Claude показать вам сырой вывод тестового запуска, а не его краткое изложение. Доверяй, но проверяй — особенно для операций с высокими ставками.

## Как всё это работает вместе

Описанные практики накапливаются. Команда с надёжным CLAUDE.md, навыками на уровне проекта, хуками, обеспечивающими их стандарты линтинга и тестирования, и привычкой к ограниченным промптам превзойдёт команду, использующую Claude Code без всего этого, в 3–5 раз на сложных инженерных задачах.

Ни одна из них не требует значительных временных вложений. Самые большие — написание CLAUDE.md и первых двух навыков — занимают один день и потом работают незаметно в фоне навсегда.
