# Шаблон CLAUDE.md — Next.js + TypeScript

`CLAUDE.md` — самый эффективный файл, который вы можете добавить в проект Claude Code. Он загружается автоматически в начале каждой сессии и обеспечивает Claude постоянным контекстом о вашем стеке, структуре, соглашениях и ограничениях — чтобы вам никогда не приходилось объяснять их заново.

Этот шаблон рассчитан на стандартный проект Next.js 15 + TypeScript. Скопируйте его в корень репозитория, заполните поля и удалите неактуальные разделы.

---

## Как использовать этот шаблон

1. Скопируйте блок кода ниже в файл `CLAUDE.md` в корне проекта.
2. Замените значения в `<угловых скобках>` на реальные данные вашего проекта.
3. Удалите разделы, которые не применимы к вашему проекту.
4. Закоммитьте `CLAUDE.md` в систему контроля версий — это документация, от которой выигрывает вся команда.

Держите `CLAUDE.md` в пределах 300 строк. Файл, требующий 15 минут на чтение, сводит на нет собственную цель.

## Шаблон

```markdown
# <Название проекта> — Контекст Claude Code

> Читать этот файл в начале каждой сессии. Не пропускать.

## Стек

- **Фреймворк:** Next.js 15, App Router, React 19
- **Язык:** TypeScript 5, включён strict mode
- **Стили:** Tailwind CSS 3, библиотека компонентов shadcn/ui
- **База данных:** PostgreSQL через Prisma ORM (или Drizzle — выберите одно)
- **Аутентификация:** NextAuth.js v5 (Auth.js)
- **Тесты:** Vitest для unit/integration, Playwright для E2E
- **Менеджер пакетов:** pnpm
- **Версия Node:** 20 LTS (см. `.nvmrc`)

## Структура проекта

```
src/
  app/           # Next.js App Router — страницы, layouts, API-маршруты
  components/    # Общие UI-компоненты
  lib/           # Бизнес-логика, утилиты, server actions
    db/          # Клиент БД и хелперы запросов
    auth/        # Утилиты аутентификации и хелперы сессий
    api/         # Обёртки для внешних API-клиентов
  hooks/         # React-хуки (только клиентская сторона)
  types/         # Общие TypeScript-типы и интерфейсы
public/          # Статические ресурсы
prisma/          # Схема и миграции (никогда не редактировать вручную)
tests/
  unit/          # Unit-тесты Vitest, зеркало структуры src/
  e2e/           # E2E-тесты Playwright
```

## Команды разработки

```bash
pnpm dev          # Запустить dev-сервер на http://localhost:3000
pnpm build        # Production-сборка (запускать перед деплоем)
pnpm test         # Запустить все unit-тесты Vitest
pnpm test:watch   # Запустить тесты в режиме watch
pnpm test:e2e     # Запустить E2E-тесты Playwright (нужен запущенный сервер)
pnpm lint         # Проверка ESLint + Prettier
pnpm lint:fix     # Автоматическое исправление ошибок линтера
pnpm db:migrate   # Применить ожидающие миграции Prisma
pnpm db:studio    # Открыть Prisma Studio на http://localhost:5555
pnpm typecheck    # Запустить tsc --noEmit
```

## Соглашения по коду

### Именование файлов
- React-компоненты: PascalCase (`UserProfile.tsx`)
- Утилиты, хуки, lib: camelCase (`useSession.ts`, `formatDate.ts`)
- Обработчики API-маршрутов: `route.ts` внутри папки маршрута
- Файлы тестов: `*.test.ts` для unit, `*.spec.ts` для E2E

### TypeScript
- Явные типы возврата обязательны на экспортируемых функциях
- Предпочитать `type` вместо `interface`, если нет наследования
- Запрещён `any` — использовать `unknown` с сужением типа
- Импортировать типы через `import type { ... }`

### Обработка ошибок
- Бизнес-логика: использовать паттерн `Result<T, E>` (см. `src/types/result.ts`), не try/catch
- API-маршруты: возвращать типизированные объекты ошибок `{ error: string; code: string }`
- Клиентские компоненты: использовать error boundaries, не try/catch inline в рендере

### База данных
- Все запросы к БД находятся в `src/lib/db/` — никогда не запрашивать напрямую из компонентов или API-маршрутов
- Каждый файл запросов экспортирует типизированные функции; сырой Prisma-клиент остаётся в `src/lib/db/client.ts`
- Транзакции для любой операции, затрагивающей более одной таблицы

### Компоненты
- Server Components по умолчанию — `"use client"` добавлять только при необходимости
- Интерфейсы пропсов в том же файле, что и компонент
- Компоненты shadcn/ui находятся в `src/components/ui/` — не редактировать сгенерированные файлы напрямую

## Переменные окружения

Требуются в `.env.local` для локальной разработки:

```
DATABASE_URL=postgresql://...
NEXTAUTH_SECRET=...
NEXTAUTH_URL=http://localhost:3000
# Добавьте свои ниже
```

Никогда не коммитить `.env.local` или `.env`. Production-секреты хранятся в настройках окружения <Vercel / Railway / вашей платформы>.

## Тесты

- Unit-тесты должны находиться в `tests/unit/` и отражать структуру `src/`
- Каждая новая функция в `src/lib/` требует как минимум теста успешного сценария и теста обработки ошибок
- Тесты Playwright выполняются против `http://localhost:3000` — сначала запустите dev-сервер
- Запускать `pnpm typecheck && pnpm lint && pnpm test` перед каждым коммитом

## Деплой

- **Платформа:** <Vercel / Railway / Fly.io>
- **Соответствие ветка → окружение:**
  - `main` → production (автодеплой при мерже)
  - `staging` → staging-окружение
- **Перед мержем в main:** CI должен пройти (lint + typecheck + tests)
- **Миграции БД:** запустить `pnpm db:migrate` в CI перед шагом деплоя

## Защищённые файлы

Никогда не изменять эти файлы напрямую — они автогенерируются или управляются инструментами:

- `prisma/migrations/` — генерируется Prisma, никогда не редактировать
- `src/components/ui/` — генерируется CLI shadcn/ui, регенерировать через `pnpm shadcn add`
- `.next/` — output сборки
- `playwright-report/` — отчёты тестов

## Словарь домена

> Использовать эти термины последовательно. Не придумывать синонимы.

- **User** — авторизованный пользователь с аккаунтом
- **Guest** — неавторизованный посетитель
- **<Термин>** — <определение>
- **<Термин>** — <определение>

## Контакты / Ответственность

- Backend / БД: <имя или команда>
- Frontend: <имя или команда>
- Инфраструктура / деплой: <имя или команда>

## Примечания к разделам

### Раздел «Стек»
Указывайте точные версии для всего, что чувствительно к версиям. «Next.js» недостаточно — «Next.js 15, App Router» говорит Claude, какие API использовать.

### Структура проекта
Не нужно перечислять каждую директорию. Сосредоточьтесь на неочевидных частях — где находится бизнес-логика, где живут запросы, почему всё организовано именно так.

### Команды
Все команды, которые может потребоваться запустить Claude при работе с кодом. Если команда требует флага или переменной окружения, укажите это здесь.

### Соглашения
Раздел с наилучшим соотношением затрат и результата. Каждое задокументированное соглашение — это комментарий код-ревью, который Claude не вынудит вас оставить.

### Защищённые файлы
Это предотвращает класс ошибок, когда Claude «улучшает» автогенерированные файлы, которые будут перезаписаны при следующем запуске инструмента.

### Словарь домена
Если в вашем кодовой базе есть бизнес-термины, отличающиеся от общепринятого использования (например, «Участник» означает что-то специфическое, отличное от «Пользователя»), задокументируйте их. Непоследовательная терминология — одна из наиболее частых причин непонимания Claude замысла разработчика.
