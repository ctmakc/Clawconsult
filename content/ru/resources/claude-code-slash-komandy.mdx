# Slash-команды в Claude Code: встроенные и кастомные

Slash-команды — это быстрые действия, которые запускаются прямо из чата Claude Code. Они делятся на два типа: встроенные команды (поставляются с Claude Code из коробки) и кастомные (которые вы определяете сами под конкретный проект или рабочий процесс). Понимание обоих типов существенно ускоряет повседневную работу.

---

## Встроенные slash-команды

Claude Code поставляется с 7 встроенными командами. Каждая решает конкретную задачу управления сессией или настройки.

### `/help`

Выводит список доступных команд и краткое описание каждой. Полезно на старте, пока интерфейс ещё не стал привычным, или чтобы проверить, какие кастомные команды зарегистрированы в текущем проекте.

```
/help
```

Вывод включает как встроенные команды, так и кастомные из `.claude/commands/`. Это хороший способ onboarding'а новых разработчиков в проект — достаточно набрать `/help` и увидеть весь набор команд команды.

**Практический совет:** Если вы только что клонировали проект и видите `.claude/commands/` в репозитории — первым делом запустите `/help`, чтобы понять, какие рабочие процессы уже автоматизированы.

---

### `/clear`

Очищает контекст текущей сессии. Все предыдущие сообщения, прочитанные файлы и накопленный контекст сбрасываются. Claude Code начинает разговор заново с чистого листа.

```
/clear
```

**Когда использовать `/clear`:**

- Завершена одна задача, начинается совершенно другая — чтобы контекст предыдущей задачи не влиял на новую
- Сессия стала длинной и контекст начал «мусорить» — Claude отвечает менее точно, потому что несёт слишком много устаревшего контекста
- Переключаетесь между разными частями кодовой базы, которые не связаны между собой

**Важный нюанс:** `/clear` не удаляет содержимое вашего CLAUDE.md и не сбрасывает настройки. Инструкции проекта остаются. Очищается только история разговора.

**Практический совет:** Воспринимайте `/clear` как `git stash` для контекста сессии. Используйте его свободно — это не разрушительная операция.

---

### `/memory`

Открывает редактор памяти Claude Code. Позволяет просматривать и редактировать то, что Claude Code сохраняет между сессиями в файле `~/.claude/projects/<project>/memory.md`.

```
/memory
```

Claude Code имеет возможность запоминать факты о проекте и предпочтениях пользователя между сессиями. `/memory` даёт прямой доступ к этому хранилищу.

**Что хранить в памяти:**

- Контекст, который CLAUDE.md не охватывает, но важен для вас лично (например, «я предпочитаю видеть полный diff перед коммитом»)
- Архитектурные решения с объяснениями («модуль auth использует JWT, а не сессии — потому что сервис stateless»)
- Ссылки на внутренние документы или задачи

**Чего не хранить в памяти:**

- Secrets и API-ключи — никогда
- Информацию, которая должна быть командной (её место в CLAUDE.md)
- Временный контекст конкретной задачи

**Практический совет:** `/memory` — личная заметка для Claude, а CLAUDE.md — командная документация. Разграничивайте их.

---

### `/model`

Переключает языковую модель прямо в сессии без перезапуска.

```
/model
```

Команда открывает интерактивный выбор из доступных моделей: Claude Opus (максимальные возможности, медленнее), Claude Sonnet (баланс скорости и качества), Claude Haiku (быстрый, для рутинных задач).

**Стратегия переключения моделей:**

Не обязательно использовать одну модель для всего. Разумный подход:

- Начинайте архитектурный разбор или сложный рефакторинг с Opus
- Переключайтесь на Sonnet для основной работы кода
- Используйте Haiku для быстрых правок, переименований, форматирования

```
/model claude-opus-4  # Для глубокого анализа
/model claude-sonnet  # Для основной разработки
```

**Практический совет:** Если Claude даёт слишком поверхностные ответы на сложный архитектурный вопрос — переключитесь на Opus через `/model` и повторите вопрос. Разница часто ощутима.

---

### `/settings`

Открывает интерактивный просмотр текущих настроек Claude Code: разрешения инструментов, конфигурация hooks, режимы работы и другие параметры.

```
/settings
```

Команда не заменяет прямое редактирование `.claude/settings.json` — она даёт быстрый read-only просмотр активной конфигурации. Полезно для диагностики: «почему Claude не может запустить этот инструмент?» — `/settings` сразу покажет, разрешён ли он.

**Практический совет:** Если инструмент заблокирован и вы не понимаете почему — `/settings` быстрее, чем читать settings.json вручную.

---

### `/review`

Запускает встроенный code review текущих изменений или указанного кода.

```
/review
/review src/auth/token.ts
```

Claude Code анализирует указанный файл или staged-изменения и даёт структурированный отзыв: потенциальные баги, проблемы безопасности, качество кода, предложения по улучшению.

**Как получить максимум от `/review`:**

Команда работает лучше с контекстом. Добавьте специфику:

```
/review — сосредоточься на безопасности и обработке ошибок
/review src/api/ — проверь только edge cases в API endpoints
/review — посмотри на производительность SQL-запросов
```

**Практический совет:** Используйте `/review` перед каждым PR — это дешевле, чем находить проблемы в code review от коллег. Claude видит паттерны, которые легко пропустить при усталости.

---

### `/init`

Инициализирует CLAUDE.md для текущего проекта — анализирует структуру репозитория и генерирует шаблон документации.

```
/init
```

Claude Code просматривает директорию проекта, читает package.json/pyproject.toml/go.mod и другие конфиги, анализирует структуру и создаёт содержательный CLAUDE.md с секциями: технологический стек, архитектура, команды для сборки/тестов, стиль кода.

**Когда запускать `/init`:**

- В начале работы с новым проектом
- После значительных изменений в архитектуре
- При онбординге Claude Code в существующий проект без CLAUDE.md

**После `/init` обязательно:**

1. Прочитайте сгенерированный CLAUDE.md
2. Уточните неточности и добавьте контекст, который Claude не мог вывести автоматически
3. Закоммитьте файл в репозиторий

**Практический совет:** Сгенерированный CLAUDE.md — хорошая стартовая точка, но не готовый документ. Потратьте 15 минут на доработку — это окупится сотнями более точных ответов Claude в будущем.

## Система кастомных slash-команд

Кастомные slash-команды — это Markdown-файлы в директории `.claude/commands/`. Каждый файл становится командой, доступной через `/имя-файла`.

### Как создать кастомную команду

1. Создайте директорию `.claude/commands/` в корне проекта
2. Создайте файл с расширением `.md`
3. Напишите промпт в теле файла

**Пример структуры:**

```
.claude/
  commands/
    release-prep.md
    db-migrate.md
    pr-description.md
    security-audit.md
```

После создания файлов они сразу доступны как:

```
/release-prep
/db-migrate
/pr-description
/security-audit
```

---

### Переменная `$ARGUMENTS`

Кастомные команды поддерживают аргументы через плейсхолдер `$ARGUMENTS`. Всё, что написано после имени команды, подставляется на место этого плейсхолдера.

```
/db-migrate add_user_email_index
```

В теле команды `$ARGUMENTS` заменяется на `add_user_email_index`.

## Практический пример 1: Release preparation

**`.claude/commands/release-prep.md`:**

```markdown
Подготовить релиз версии $ARGUMENTS.

Выполни следующие шаги последовательно:

1. Убедись, что все тесты проходят: запусти полный тестовый suite
2. Проверь, что нет незакоммиченных изменений
3. Обнови версию в package.json на $ARGUMENTS
4. Сгенерируй CHANGELOG.md на основе коммитов с момента последнего тега
5. Создай коммит с сообщением "chore: bump version to $ARGUMENTS"
6. Создай git tag v$ARGUMENTS
7. Выведи список изменений для финальной проверки перед пушем

Не пуши автоматически — жди подтверждения.
```

**Использование:**

```
/release-prep 2.4.1
```

Claude Code выполнит весь сценарий подготовки релиза, остановившись перед пушем для финального подтверждения.

## Практический пример 2: Database migration

**`.claire/commands/db-migrate.md`:**

```markdown
Создай и примени новую database migration с именем $ARGUMENTS.

Шаги:
1. Проверь текущее состояние миграций (список применённых и ожидающих)
2. Создай новый migration-файл с timestamp-префиксом и именем "$ARGUMENTS"
3. Проанализируй контекст задачи и предложи SQL для up() и down() методов
4. Покажи мне полный файл миграции для ревью
5. После моего подтверждения — примени миграцию через стандартный инструмент проекта (migrate, knex, alembic — определи по конфигурации)
6. Верифицируй, что миграция применена успешно

Если $ARGUMENTS пустой — только покажи статус текущих миграций без создания новой.
```

**Использование:**

```
/db-migrate add_refresh_token_expiry_to_users
/db-migrate  # Только статус
```

## Практический пример 3: Генерация описания PR

**`.claude/commands/pr-description.md`:**

```markdown
Сгенерируй описание pull request для текущей ветки.

1. Получи diff относительно main: git diff main...HEAD
2. Прочитай коммиты этой ветки: git log main..HEAD --oneline
3. Если передан аргумент "$ARGUMENTS" — используй его как дополнительный контекст о задаче или ссылку на тикет
4. Создай описание PR в формате Markdown:

## Что изменилось
- [Bullet points с конкретными изменениями]

## Почему
[Объяснение проблемы или задачи, которую решает PR]

## Как тестировать
- [ ] [Конкретные шаги для тестирования]

## Замечания для ревьюера
[Всё, на что стоит обратить особое внимание]

$ARGUMENTS

5. Выведи готовый текст — я скопирую его в GitHub/GitLab
```

**Использование:**

```
/pr-description PROJ-142: исправить истечение session token
```

## Практический пример 4: Security audit

**`.claude/commands/security-audit.md`:**

```markdown
Проведи security audit для $ARGUMENTS (файл, директория или модуль).

Если $ARGUMENTS пустой — проанализируй весь проект.

Проверь:
1. Жёстко прописанные credentials и secrets в коде
2. SQL injection: неэкранированные пользовательские данные в запросах
3. XSS: непроверенный вывод в HTML-шаблонах
4. Небезопасные зависимости: запусти npm audit / pip-audit / go mod tidy
5. Аутентификация и авторизация: проверь граничные случаи
6. Обработка ошибок: не раскрываются ли stack traces пользователям
7. CORS и заголовки безопасности в HTTP-ответах

Выведи структурированный отчёт:
- КРИТИЧНО: немедленное исправление
- ВЫСОКИЙ: исправить до релиза
- СРЕДНИЙ: запланировать исправление
- НИЗКИЙ: рекомендации

Для каждой проблемы — конкретный файл, строка и рекомендуемое исправление.
```

**Использование:**

```
/security-audit src/api/
/security-audit  # Весь проект
```

## Лучшие практики именования кастомных команд

**Используйте kebab-case:**

```
release-prep.md     ✓
releasePrep.md      ✗
release_prep.md     ✗  (работает, но непоследовательно)
```

**Делайте имена глаголами или глагол-объект:**

```
deploy.md           ✓
db-seed.md          ✓
security-check.md   ✓
database.md         ✗  (непонятно, что делает)
```

**Группируйте связанные команды через префикс:**

```
db-migrate.md
db-seed.md
db-reset.md

deploy-staging.md
deploy-production.md
```

**Избегайте имён, конфликтующих со встроенными командами:**

```
/help, /clear, /memory, /model, /settings, /review, /init
```

Кастомная команда с тем же именем переопределит встроенную — это редко желаемое поведение.

## Организация кастомных команд в команде

Файлы в `.claude/commands/` коммитятся в репозиторий — это означает, что все кастомные команды автоматически доступны каждому разработчику, клонировавшему проект. Это мощный инструмент стандартизации рабочих процессов.

**Рекомендуемая структура для зрелой команды:**

```
.claude/
  commands/
    # Разработка
    pr-description.md
    security-audit.md
    
    # Релизы
    release-prep.md
    changelog.md
    
    # Базы данных
    db-migrate.md
    db-seed.md
    db-reset.md
    
    # Диагностика
    debug-env.md
    health-check.md
```

Документируйте команды в README или CLAUDE.md, чтобы новые разработчики знали об их существовании до первого `/help`.

## Разница между кастомными командами и CLAUDE.md

| | Кастомные команды | CLAUDE.md |
|--|------------------|----|
| Когда применяется | При явном вызове `/command` | При каждом сообщении |
| Содержимое | Пошаговый промпт для конкретной задачи | Постоянный контекст и правила |
| Аргументы | Через `$ARGUMENTS` | Нет |
| Лучше для | Повторяющихся процессов | Стиля, архитектуры, соглашений |

Оба механизма дополняют друг друга. CLAUDE.md задаёт «как работаем в этом проекте», кастомные команды автоматизируют «как делаем конкретные вещи».
