# Claude Code работает медленно? Диагностика и решения

**Проблема**: Ответы Claude Code ощущаются вялыми — вы ждёте несколько секунд (или намного дольше) между отправкой сообщения и появлением вывода, или вызовы инструментов занимают значительно больше времени, чем должны.

Медленная работа Claude Code почти всегда имеет конкретную корневую причину. Этот гайд рассматривает наиболее распространённые из них в порядке частоты, даёт чеклист для изоляции проблемы и конкретный фикс для каждой.

---

## Симптомы

- Ответы занимают 10–30+ секунд там, где раньше были почти мгновенными
- Claude долго «думает» перед тем, как начать выводить результат
- Вызовы инструментов (bash, чтение файлов, MCP) ощущаются медленнее, чем сами операции
- Стриминг ответа начинается, потом зависает, потом продолжается рывками
- Производительность была нормальной в начале сессии, но деградировала по ходу работы

---

## Чеклист диагностики

Пройдитесь по этим вопросам перед тем, как приступать к фиксам:

1. Замедление началось в середине сессии (раздутие контекста) или с первого сообщения (проблема конфигурации или модели)?
2. Используете ли вы MCP-серверы? Их отключение ускоряет работу?
3. Какую модель используете — Sonnet или Opus?
4. Какой длины ваш файл CLAUDE.md?
5. Вы видите реальные задержки в ответе API или задержки, пока Claude обрабатывает задачу (выводит шаги размышления)?
6. Вы на платном API-плане или используете бесплатный/пробный ключ?

---

## Причина 1: Раздутие контекстного окна

**Это наиболее частая причина деградации производительности в рамках сессии.**

Claude обрабатывает каждый токен в контексте разговора при каждом ответе. По мере роста сессии — особенно если вы вставляли большие файлы, читали код на несколько тысяч строк или выполняли много вызовов инструментов — контекстное окно заполняется. Каждый новый ответ требует обработки всего накопленного контекста, что линейно увеличивает время вычислений и латентность API.

**Признаки раздутия контекста:**
- Производительность была нормальной в начале сессии
- Вы работаете в одной сессии 30+ минут
- Вы просили Claude читать много больших файлов

**Фикс: запустите `/compact`**

Команда `/compact` резюмирует текущую историю разговора в сжатую форму, резко сокращая количество токенов при сохранении существенного контекста того, над чем вы работали.

```
/compact
```

Запускайте эту команду в естественных точках разрыва — после завершения фичи, после отладочной сессии, или когда замечаете рост времени ответа. Это занимает несколько секунд, но может сократить размер контекста на 70–90%, мгновенно восстанавливая скорость ответа.

**Дополнительная гигиена контекста:**
- Избегайте вставки целых больших файлов в разговор. Вместо этого позвольте Claude использовать инструмент `Read` для доступа к конкретным диапазонам строк.
- Закончив изучение, явно скажите Claude: «Тебе больше не нужно помнить содержимое файла X». Это сигнализирует ему отбросить этот контент из рабочей памяти при следующем compact.

## Причина 2: Загрузка CLAUDE.md на каждый запрос

Claude Code читает ваш файл CLAUDE.md в начале каждого взаимодействия. Длинный CLAUDE.md напрямую добавляет к базовому контексту каждого сообщения — даже коротких вроде «запусти тесты».

**Признаки:**
- Первый ответ в сессии уже медленный, до того как контекст накопился
- CLAUDE.md занимает несколько сотен строк или больше

**Фикс: держите CLAUDE.md кратким**

CLAUDE.md должен быть компактным справочным документом — контекст проекта, ключевые команды, запрещённые паттерны, правила стиля кода. Он не должен содержать:

- Длинных объяснений в прозе
- Контента онбординга, нужного только новым членам команды
- Закомментированных старых инструкций
- Заметок по задачам или обновлений статуса

Хорошо оптимизированный CLAUDE.md — менее 100 строк. Пример компактной структуры:

```markdown
# Проект: MyApp

## Стек
Node 20, TypeScript, PostgreSQL, Prisma, Next.js 14

## Команда тестирования
pnpm test

## Правила кода
- Никакого `any` в TypeScript
- Весь доступ к БД через Prisma client (никогда raw SQL)
- Запускать `pnpm lint` перед коммитом

## Запрещено
- Никогда не редактировать сгенерированные файлы в /generated/
- Никогда не коммитить .env файлы
```

Если CLAUDE.md длинный из-за охвата нескольких подпроектов — рассмотрите разделение: поместите CLAUDE.md для конкретных проектов в поддиректории, а корневой сделайте минимальным.

## Причина 3: Латентность MCP-сервера

Каждый вызов MCP-инструмента добавляет круговую поездку: Claude генерирует вызов инструмента, ваш MCP-сервер получает его, выполняет действие и возвращает результат. Если настроено несколько MCP-серверов, Claude может последовательно вызвать несколько инструментов, каждый из которых добавляет латентность.

**Признаки:**
- Медлительность возникает именно когда Claude использует инструменты (вы видите вызовы инструментов в выводе)
- Производительность нормальная для текстовых ответов, но деградирует когда Claude обращается к файлам или внешним сервисам

**Диагностика медленного MCP-сервера:**

```bash
# Проверить логи MCP-серверов (для локальных серверов)
tail -f /tmp/mcp-*.log

# Напрямую протестировать время ответа MCP-сервера
time npx @modelcontextprotocol/inspector
```

**Фиксы:**
- Удалите из конфигурации MCP-серверы, которые не используете активно. Каждый подключённый сервер добавляет накладные расходы на запуск.
- Для локальных файловых операций предпочитайте встроенные файловые инструменты Claude Code вместо filesystem MCP-сервера — встроенные инструменты не требуют круговых поездок.
- Если удалённый MCP-сервер (например, MCP базы данных, указывающий на облачную БД) работает медленно — проверьте, не является ли узким местом сам сервис.

## Причина 4: Выбор модели — Sonnet vs. Opus

Claude Code по умолчанию использует claude-sonnet-4-5 для большинства задач, но некоторые конфигурации или явные флаги модели могут переключить его на Opus. Разница во времени ответа существенная:

| Модель | Скорость | Глубина рассуждений | Лучше всего для |
|--------|----------|---------------------|-----------------|
| claude-sonnet-4-5 | Быстрая (2–8с типично) | Сильная | Большинство задач разработки |
| claude-opus-4 | Медленнее (10–30с типично) | Наибольшая | Сложные многошаговые рассуждения, архитектурные решения |

**Фикс: используйте Sonnet для задач, чувствительных к скорости**

```bash
claude --model claude-sonnet-4-5
```

Используйте Opus, когда нужна максимальная глубина рассуждений — сложное проектирование алгоритмов, архитектурные решения или отладка особенно каверзных проблем. Для рутинных правок файлов, написания тестов и генерации кода Sonnet даёт практически идентичный результат при доле задержки.

## Причина 5: Таймауты bash-команд

Когда Claude выполняет bash-команды, он ждёт их завершения перед продолжением. Если ваши команды долго выполняются (процессы сборки, тест-сьюты, запуск серверов), Claude выглядит «замёрзшим» в ожидании.

Это не Claude работает медленно — он корректно ждёт вашего инструментария. Но ощущается как плохая производительность.

**Фикс: понять, чего ждёт Claude**

Когда долго нет вывода, проверьте, выполняет ли Claude команду:
- Ищите `Bash (running...)` в отображении вызовов инструментов
- Сама команда может быть узким местом (тест-сьют на 60 секунд всегда будет занимать 60 секунд)

Если вам нужно, чтобы Claude продолжал работать, пока выполняется долгий процесс, используйте фоновые процессы:

```bash
# Скажите Claude: «Запусти dev-сервер в фоне, затем продолжай»
npm run dev &
```

Можно также скорректировать ожидания в CLAUDE.md:

```markdown
## Заметки об окружении
- `pnpm test` занимает ~90 секунд для полного сьюта — это ожидаемо
- Используйте `pnpm test --testPathPattern=<файл>` для запуска одного файла
```

Этот контекст помогает Claude принимать более взвешенные решения о том, какие команды запускать.

## Причина 6: Rate limit vs. медленные ответы

Ошибки rate limit и медленные ответы выглядят похоже, но их можно перепутать:

- **Rate limit**: Claude Code возвращает явную ошибку (`rate limit exceeded`) и останавливается
- **Медленный ответ**: Claude продолжает работать, просто медленно

Если вы достигаете rate limit — смотрите наш [гайд по rate limit](/resources/rate-limit). Но если ответы медленные без ошибки — rate limit не причина.

**Одно исключение**: если вы на низком API-тарифе, могут действовать лимиты конкурентности, создающие задержки очереди без явной ошибки rate limit. В этом случае помогает апгрейд плана или запрос на увеличение лимита.

## Причина 7: Сетевая латентность

Claude Code взаимодействует с API Anthropic по HTTPS. При медленном или нестабильном сетевом подключении каждая круговая поездка к API добавляет латентность.

**Диагностика:**

```bash
# Проверить латентность до API Anthropic
curl -o /dev/null -s -w "Время: %{time_total}s\n" https://api.anthropic.com/

# Проверить потерю пакетов
ping -c 10 api.anthropic.com
```

Если латентность до API выше 300мс или есть потеря пакетов — сеть является узким местом. Варианты:
- Используйте проводное соединение вместо Wi-Fi
- Переключитесь на другую сеть
- Если используете VPN, попробуйте маршрутизировать трафик API в обход VPN

## Итог: чеклист фиксов производительности

| Симптом | Наиболее вероятная причина | Фикс |
|---------|--------------------------|------|
| Замедляется в длинной сессии | Раздутие контекста | `/compact` |
| Медленно с первого сообщения | Длинный CLAUDE.md | Сократить CLAUDE.md |
| Медленно именно при вызовах инструментов | Латентность MCP | Удалить неиспользуемые MCP-серверы |
| Стабильно медленно независимо от сессии | Неправильная модель | `--model claude-sonnet-4-5` |
| Зависает при командах | Долго выполняющийся bash | Ожидаемо — проверить что выполняется |
| Медленно на всех запросах, нет ошибки rate limit | Сетевая латентность | Проверить `ping api.anthropic.com` |

## Всё ещё медленно?

Если вы прошли чеклист, но производительность всё ещё плохая — следующий шаг: точно измерить, где уходит время:

1. Начните свежую сессию Claude Code (устраняет раздутие контекста)
2. Используйте минимальный CLAUDE.md (исключает накладные расходы CLAUDE.md)
3. Временно отключите все MCP-серверы (изолирует MCP как переменную)
4. Запустите простой промпт и замерьте время: «Сколько будет 2+2?»

Если этот простой промпт всё ещё медленный — проблема, вероятно, на стороне API (rate limiting, уровень тарифа или региональная латентность API). Обратитесь в поддержку Anthropic или свяжитесь с нами в ClawHelp для глубокой диагностической сессии.
