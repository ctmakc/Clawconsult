# Git-воркфлоу с Claude Code: лучшие практики

Claude Code может управлять всем вашим git-воркфлоу — от staging и коммитов до создания веток, rebase и открытия pull request. При грамотном подходе это даёт кратный прирост производительности. При небрежном — вы рискуете получить запутанную историю, потерянную работу или коммиты, которые не собирались пушить.

В этом руководстве — практики, которые поддерживают чистоту git-воркфлоу при работе с ИИ-коллаборатором.

---

## Как Claude Code работает с git

У Claude Code есть прямой доступ к шеллу, и он воспринимает git как стандартный инструмент. По умолчанию он будет:

- Стейджить файлы через `git add`
- Делать коммиты с описательным сообщением, которое он генерирует сам
- Создавать ветки при необходимости для изолированных изменений
- Читать историю git, чтобы понять соглашения вашего проекта
- Открывать PRs через CLI `gh`, если он установлен

У него нет собственных предпочтений по воркфлоу — он следует тем соглашениям и ограничениям, которые вы ему задаёте. Это значит, что качество ваших git-выходных данных напрямую определяется тем, насколько чётко вы формулируете ожидания.

## Качество commit-сообщений

Claude Code генерирует commit-сообщения, анализируя diff и выводя намерение. Качество, как правило, хорошее, но его можно улучшить, передав Claude контекст, которого diff сам по себе не содержит.

**Что делает хорошее commit-сообщение для Claude:**

Объясните *почему*, а не только *что*. Сравните:

- «Закоммить эти изменения» — Claude пишет механическое описание диффа
- «Закоммить этот фикс. Баг был в том, что session tokens не обновлялись по истечении срока, вызывая тихий logout.» — Claude пишет сообщение, которое отражает корневую причину

**Задайте соглашения в CLAUDE.md:**

```markdown
## Стиль коммитов
- Повелительное наклонение: «Добавить фичу» а не «Добавлена фича»
- Тема не более 50 символов
- Если работаете по задаче, включать номер тикета: «Починить обновление токена (PROJ-142)»
- Тело объясняет *почему*, а не *что*
```

Claude прочтёт это и применит правила при генерации commit-сообщений.

**Всегда проверяйте перед тем, как Claude сделает коммит.** Воркфлоу должен быть таким:

1. Claude стейджит изменения
2. Вы проверяете: `git diff --staged`
3. Вы подтверждаете коммит или просите Claude скорректировать сообщение
4. Claude коммитит

Если пропустить шаг проверки, можно получить коммиты, которые не соответствуют стилю истории проекта, или включают файлы, которые не планировалось стейджить.

## Просмотр диффов перед коммитом

Самая важная git-привычка при работе с Claude Code: **всегда запускайте `git diff --staged` перед тем, как подтвердить коммит.**

```bash
git diff --staged
```

Это показывает ровно то, что будет закоммичено. Claude Code работает с высокой уверенностью и может застейджить больше, чем вы ожидали — например, конфигурационный файл, который он изменил как побочный эффект основной задачи, или отладочный лог, который вы добавили временно.

**Сделайте просмотр диффов рефлексом.** Если вы используете Claude Code в терминале — запускайте `git diff --staged` сами перед тем, как сказать «да, коммить». Если Claude Code предлагает коммит, скажите ему: «Сначала покажи `git diff --staged`, потом закоммитим».

Можно также добавить хук, который открывает дифф автоматически (см. Pre-commit хуки ниже).

## Соглашения именования веток

Когда Claude Code создаёт ветки, он генерирует имена на основе текущей задачи. Имена по умолчанию обычно разумные (`fix-auth-token-refresh`, `add-user-export-endpoint`), но могут не совпадать с соглашением вашего проекта.

**Задайте правила именования веток в CLAUDE.md:**

```markdown
## Именование веток
- Фича-ветки: feature/<короткое-описание>
- Баг-фиксы: fix/<короткое-описание>
- Хотфиксы: hotfix/<короткое-описание>
- Включать номер тикета: feature/PROJ-142-user-export
```

Claude будет следовать этим паттернам при создании веток. Это особенно важно в командной работе, где имена веток влияют на поведение CI или интеграцию с системами управления задачами (Jira, YouTrack и т.д.).

## Когда использовать worktrees

Git worktrees позволяют одновременно чекаутить несколько веток в отдельных директориях. Claude Code поддерживает это нативно — особенно полезно для:

- Работы над багфиксом, пока Claude продолжает разработку фичи на другой ветке
- Ревью PR-ветки коллеги без нарушения вашей рабочей директории
- Параллельных сессий Claude Code на разных частях кодовой базы

**Базовая настройка worktree:**

```bash
# Создать worktree для хотфикса, пока основная разработка продолжается
git worktree add ../myapp-hotfix hotfix/critical-auth-bug

# Claude Code можно направить в любую директорию
cd ../myapp-hotfix
claude
```

**Когда worktrees — правильный выбор:**
- У вас две действительно независимые задачи, которые не должны делить рабочее состояние
- Нужно запустить тесты на ветке, не переключая основное окружение
- Ведёте параллельные сессии Claude Code в одном репозитории

**Когда worktrees — излишество:**
- Простые последовательные задачи — закончи одну, приступай к следующей
- Задачи, которые делят файлы или конфигурацию

## Pre-commit хуки и Claude Code

Pre-commit хуки запускаются автоматически перед каждым коммитом. Claude Code уважает их — он не обойдёт хуки флагом `--no-verify`, если вы явно не попросите (и предупредит, если вы попытаетесь).

**Это фича, а не ограничение.** Хуки — ваши контрольно-пропускные пункты качества. Распространённые хуки, которые хорошо работают с Claude Code:

```bash
# пример .husky/pre-commit
#!/bin/sh
pnpm lint
pnpm test --passWithNoTests
```

Если pre-commit хук упадёт, Claude Code увидит вывод ошибки и, как правило:
1. Объяснит, что пошло не так
2. Исправит проблему
3. Повторно застейджит и попытается закоммитить снова

Этот цикл хорошо работает для ошибок линтинга. При падении тестов Claude Code обычно расследует и устраняет корневую причину перед повторной попыткой.

**Критически важно: никогда не просите Claude пропускать хуки.** Хуки существуют, чтобы ловить проблемы до того, как они попадут в репозиторий. Если хук падает и у вас возникает соблазн его обойти — правильный ответ: исправить лежащую в основе проблему. Claude Code поможет с этим.

## Паттерны .gitignore для Claude Code

Claude Code создаёт несколько локальных файлов, которые, как правило, не стоит коммитить:

```gitignore
# Локальный конфиг Claude Code (может содержать персональные настройки)
.claude/settings.local.json

# Если используете настройки уровня проекта, которые разделяются командой — коммитьте:
# .claude/settings.json  ← обычно безопасно коммитить
# .claude/CLAUDE.md      ← это инструкции проекта, коммитьте

# Никогда не коммитить
.claude/settings.local.json
```

**Что коммитить и что нет:**

| Файл | Коммитить? | Причина |
|------|------------|---------|
| `CLAUDE.md` (корень) | Да | Общие инструкции проекта |
| `.claude/settings.json` | Обычно да | Общие разрешения инструментов |
| `.claude/settings.local.json` | Нет | Персональные переопределения |
| `.claude/projects/` | Нет | Личная память сессий |

Если в вашей директории `.claude/` есть API-ключи или персональная конфигурация — добавьте её целиком в `.gitignore`. Используйте переменные окружения для credentials, а не конфигурационные файлы.

## Stash перед крупными рефакторингами

Перед тем как просить Claude сделать масштабный рефакторинг, сохраните текущую незавершённую работу:

```bash
git stash push -m "WIP: до рефакторинга Claude для модуля auth"
```

Это даёт вам чистую точку отката. Если рефакторинг пойдёт не так — Claude неверно понял область, сделал неожиданные изменения или сломал что-то неочевидное — вы сможете восстановить предыдущее состояние:

```bash
git stash pop
```

**Когда делать stash перед задачей Claude Code:**
- «Отрефактори весь модуль аутентификации»
- «Переименуй эту концепцию по всей кодовой базе»
- «Преобразуй этот class-based компонент в hooks везде»
- Любая задача, где в описании есть «все файлы» или «везде»

Для точечных правок (исправить эту функцию, добавить этот endpoint) stash обычно не нужен. Для широких структурных изменений — это дешёвая страховка.

## Rebase vs. merge feature-веток

Когда Claude Code создаёт feature-ветку и вы хотите интегрировать её в main, есть два варианта: rebase или merge. Claude Code будет следовать той стратегии, которую вы укажете.

**Merge** (`git merge feature/my-branch`):
- Сохраняет точную историю того, когда были сделаны изменения
- Создаёт merge-коммит
- Легче понять «что произошло и когда»
- Лучше для команд, которым важна историческая точность

**Rebase** (`git rebase main`):
- Воспроизводит коммиты feature-ветки поверх текущего tip main
- Создаёт линейную историю
- Делает `git log` удобнее для чтения
- Лучше, если хотите чистую линейную историю проекта

**Рекомендация для воркфлоу с Claude Code**: используйте rebase + squash для небольших feature-веток, которые создаёт Claude. Это сохраняет историю main чистой без шума промежуточных коммитов, которые Claude делал в процессе поиска решения.

```bash
# Squash всех коммитов feature-ветки в один чистый коммит
git rebase -i main
# Затем выбрать 'squash' для всех коммитов кроме первого
```

Или скажите Claude: «Squash все коммиты этой ветки в один с чистым итоговым сообщением, затем смержи в main».

## Качество описаний pull request

Когда вы просите Claude Code открыть pull request, он генерирует описание на основе изменений. Качество этого описания зависит от доступного контекста.

**Советы по улучшению описаний PR:**

1. **Скажите Claude, что PR должен решить, до того как он пишет описание.** «Открой PR — это исправляет баг с истечением сессии, о котором сообщалось в issue #142. Корневая причина: refresh tokens не проверялись перед аутентифицированными запросами.»

2. **Ссылайтесь на issues.** Claude свяжет GitHub issues, если вы их упомяните: «Это закрывает #142.»

3. **Настройте шаблон PR.** Добавьте `.github/PULL_REQUEST_TEMPLATE.md` — Claude будет использовать его как структурный ориентир.

4. **Проверяйте описание перед отправкой.** Описания PR от Claude Code — хорошая отправная точка, но могут упустить бизнес-контекст, соображения безопасности или замечания по миграции, которые нужны человеку-ревьюеру.

**Пример промпта для качественного PR:**

```
Открой PR из этой ветки в main.
Заголовок: «Исправить обработку истечения session token»
- Закрывает issue #142
- Включить: что изменилось, почему было сломано, как тестировать
- Отметить, что перед деплоем нужна миграция базы данных
```

## Распространённые ошибки

**1. Давать Claude коммитить без проверки `git diff --staged`**
Всегда проверяйте, что застейджено. Claude точен, но не безошибочен — он может застейджить файлы, которые не стоило.

**2. Не задавать git-соглашения в CLAUDE.md**
Без инструкций Claude коммитит в общем стиле, который может не соответствовать вашему проекту. Инвестируйте 5 минут в написание соглашений по коммитам и веткам.

**3. Просить Claude делать force-push в shared-ветки**
Никогда не инструктируйте Claude делать `git push --force` в main или любую ветку, которую разделяет команда. Легитимные сценарии force-push (перезапись истории feature-ветки перед мержем) допустимы на приватных ветках.

**4. Пропускать pre-commit хуки**
Не просите Claude использовать `--no-verify`. Исправьте лежащую в основе проблему.

**5. Делать крупные рефакторинги без stash**
Сначала stash. Две минуты того стоят.

## Рекомендуемая git-секция в CLAUDE.md

Готовая к использованию git-секция для вашего CLAUDE.md:

```markdown
## Git-воркфлоу

### Commit-сообщения
- Повелительное наклонение, тема 50 символов
- Тело: объяснять *почему*, а не *что*
- Ссылаться на тикеты: «Починить timeout авторизации (PROJ-89)»

### Ветки
- feature/<описание> для новых фич
- fix/<описание> для багфиксов
- Всегда ветвиться от main, если не указано иное

### Правила
- Всегда запускать `git diff --staged` перед коммитом — показывать вывод
- Никогда не использовать --no-verify
- Никогда не делать force-push в main или develop
- Stash перед крупными рефакторингами

### Описания PR
- Включать: что изменилось, почему, как тестировать
- Ссылаться на связанные issues
- Указывать шаги миграции или деплоя
```

С этой секцией в CLAUDE.md, Claude Code будет последовательно следовать вашим соглашениям на протяжении каждой сессии.
