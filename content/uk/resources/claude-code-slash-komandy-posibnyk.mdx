# Slash-команди в Claude Code: вбудовані та власні

Slash-команди — це швидкий спосіб запускати повторювані дії в Claude Code без написання довгих промптів щоразу. Введіть `/` у терміналі — і отримаєте список доступних команд. Деякі вбудовані, деякі ви можете визначити самостійно під свій проект і стек.

У цьому посібнику — повний розбір усіх 7 вбудованих команд і детальний гід по створенню власних з прикладами, які можна використовувати в реальних проектах.

---

## Що таке slash-команди

Slash-команди — це скорочення, доступні в інтерактивному режимі Claude Code (REPL). Вони починаються з символу `/` і можуть приймати аргументи.

**Два типи slash-команд:**

1. **Вбудовані** — реалізовані всередині Claude Code, не потребують конфігурації
2. **Кастомні** — визначаються у файлах `.claude/commands/*.md`, специфічні для проекту або користувача

**Де вони зберігаються:**

- Проектні кастомні команди: `.claude/commands/` (комітяться в репозиторій, доступні всій команді)
- Користувацькі команди: `~/.claude/commands/` (доступні у всіх проектах для конкретного користувача)

---

## Вбудовані slash-команди

### `/help`

Відображає список усіх доступних команд — і вбудованих, і кастомних — з коротким описом кожної.

```
/help
```

Корисно після додавання нових команд у проект, щоб переконатись, що вони правильно підхоплюються.

---

### `/clear`

Очищає контекст поточної сесії та починає розмову з чистого аркуша. Розмовна історія видаляється, але стан файлової системи залишається незмінним.

```
/clear
```

**Коли використовувати:** при переключенні між непов'язаними завданнями в рамках однієї сесії; коли контекст «засмітився» помилковими прийняттями рішень; після великих рефакторингів, щоб уникнути плутанини зі старим станом коду.

---

### `/memory`

Відкриває файл пам'яті поточної сесії для перегляду та редагування. Файли пам'яті — це `CLAUDE.md` файли у різних рівнях ієрархії проекту.

```
/memory
```

Claude Code підтримує ієрархічну пам'ять:
- `~/.claude/CLAUDE.md` — глобальна пам'ять (застосовується до всіх проектів)
- `<project>/.claude/CLAUDE.md` або `<project>/CLAUDE.md` — пам'ять проекту
- `<subdirectory>/CLAUDE.md` — пам'ять піддиректорії

Команда `/memory` дозволяє переглянути і редагувати ці файли, не виходячи з Claude Code.

---

### `/model`

Перемикає мовну модель, яку використовує Claude Code у поточній сесії.

```
/model claude-opus-4-5
/model claude-sonnet-4-5
/model claude-haiku-4-5
```

**Практичне застосування:** використовуйте Sonnet або Haiku для рутинних завдань (редагування, форматування, пошук), а Opus — для складних архітектурних рішень або code review. Це суттєво зменшує витрати на API без втрати якості в повсякденній роботі.

---

### `/settings`

Відкриває поточні налаштування Claude Code у доступному для редагування форматі. Показує активну конфігурацію, включно зі значеннями permissions, hooks та інших параметрів.

```
/settings
```

Аналог перегляду `.claude/settings.json`, але з інтерактивним інтерфейсом всередині Claude Code.

---

### `/review`

Запускає code review поточних змін або вказаного файлу. Claude Code аналізує код з точки зору якості, безпеки, продуктивності та відповідності стандартам проекту.

```
/review
/review src/api/users.ts
```

Без аргументів — review staged змін (git diff --staged). З аргументом — review конкретного файлу. Ця команда особливо корисна перед комітом або pull request.

---

### `/init`

Ініціалізує `CLAUDE.md` файл для поточного проекту. Claude Code аналізує структуру репозиторію, `package.json`, `pyproject.toml` та інші конфігураційні файли, а потім генерує контекстний `CLAUDE.md` з документацією проекту.

```
/init
```

Запускайте `/init` на початку роботи з новим репозиторієм або після значних структурних змін у проекті. Згенерований файл слід відредагувати, додавши специфічні бізнес-правила та домовленості команди.

---

## Кастомні slash-команди

Кастомні команди — це Markdown-файли у директорії `.claude/commands/`. Ім'я файлу визначає ім'я команди:

- `.claude/commands/release-prep.md` → `/release-prep`
- `.claude/commands/db-migrate.md` → `/db-migrate`

**Структура файлу команди:**

```markdown
---
description: "Коротке описання команди (відображається в /help)"
---

Ваш промпт тут. Він може бути багаторядковим і містити
будь-які інструкції для Claude Code.

Для підстановки аргументів використовуйте $ARGUMENTS.
```

### Спеціальна змінна `$ARGUMENTS`

При виклику `/my-command деякий аргумент` змінна `$ARGUMENTS` буде замінена на `деякий аргумент` у тілі промпту.

```
/deploy staging    → $ARGUMENTS = "staging"
/review src/auth   → $ARGUMENTS = "src/auth"
```

Якщо команда не потребує аргументів — просто не включайте `$ARGUMENTS` у файл.

## Приклад 1: `/release-prep`

Автоматизує підготовку до release: перевірка тестів, оновлення CHANGELOG, бамп версії.

**`.claude/commands/release-prep.md`:**

```markdown
---
description: "Підготовка до release: тести, CHANGELOG, версія"
---

Підготуй проект до release версії $ARGUMENTS. Виконай такі кроки:

1. Запусти повний набір тестів (`npm test` або `pytest`) і переконайся, що всі проходять.
2. Перевір git log з останнього тегу і склади список змін.
3. Онови CHANGELOG.md — додай секцію для версії $ARGUMENTS з датою сьогодні.
4. Онови версію в package.json (або pyproject.toml) до $ARGUMENTS.
5. Створи git commit з повідомленням "chore: prepare release $ARGUMENTS".
6. Виведи підсумок: що змінилось, скільки тестів пройшло, які файли оновлено.

Якщо тести впадуть — зупинись і поясни, що потрібно виправити перед release.
```

**Використання:**

```
/release-prep 2.4.0
```

## Приклад 2: `/db-migrate`

Управляє міграціями бази даних із валідацією перед застосуванням.

**`.claude/commands/db-migrate.md`:**

```markdown
---
description: "Створення та застосування міграцій БД"
---

Виконай міграцію бази даних: $ARGUMENTS

Якщо $ARGUMENTS містить опис змін (наприклад, "add users table" або "add index on email"):
1. Згенеруй файл міграції за допомогою міграційного інструменту проекту (Prisma, Alembic, Knex, Flyway тощо).
2. Покажи мені згенерований SQL перед застосуванням.
3. Перевір, чи міграція оборотна (є DOWN migration).
4. Застосуй міграцію на dev-середовищі.
5. Оновлю schema-файл або моделі, якщо потрібно.

Якщо $ARGUMENTS — це "rollback":
1. Покажи список останніх 5 міграцій.
2. Запитай, яку саме відкотити.
3. Виконай rollback і підтвердь результат.

Якщо $ARGUMENTS — це "status":
1. Покажи список усіх міграцій з їх статусом (applied/pending).
```

**Використання:**

```
/db-migrate add index on users.email
/db-migrate rollback
/db-migrate status
```

## Приклад 3: `/pr-description`

Генерує опис pull request на основі diff і контексту проекту.

**`.claude/commands/pr-description.md`:**

```markdown
---
description: "Генерація опису PR для поточних змін"
---

Згенеруй повний опис pull request для поточних змін.

1. Проаналізуй `git diff main...HEAD` — всі зміни відносно main.
2. Перегляни `git log main...HEAD --oneline` — список комітів.
3. Склади опис PR у такому форматі:

## Що змінилось
[1-3 bullet points з ключовими змінами]

## Чому це потрібно
[Контекст і мотивація змін]

## Як тестувати
[Конкретні кроки для тестування PR]

## Checklist
- [ ] Тести написані/оновлені
- [ ] Документація оновлена (якщо потрібно)
- [ ] Breaking changes задокументовані (якщо є)
- [ ] Міграції БД перевірені (якщо є)

$ARGUMENTS

Виведи готовий текст, який можна скопіювати в GitHub/GitLab.
```

**Використання:**

```
/pr-description
/pr-description Зверни увагу: це breaking change для API v1
```

## Приклад 4: `/security-audit`

Запускає аудит безпеки вказаного модуля або всього проекту.

**`.claude/commands/security-audit.md`:**

```markdown
---
description: "Аудит безпеки коду — вразливості, залежності, конфігурація"
---

Проведи аудит безпеки: $ARGUMENTS

Перевір наступне:

**1. Вразливості коду:**
- SQL injection (параметризовані запити?)
- XSS (екранування виводу?)
- CSRF (захист форм?)
- Відкриті редіректи
- Небезпечна десеріалізація
- Path traversal

**2. Аутентифікація та авторизація:**
- Чи всі ендпоінти захищені?
- Чи перевіряються права доступу на рівні ресурсу?
- JWT/сесії — термін дії, зберігання, ротація

**3. Залежності:**
- Запусти `npm audit` або `pip-audit` або `bundle audit`
- Виведи критичні та high-severity вразливості

**4. Конфігурація:**
- Секрети в коді (API ключі, паролі)
- Небезпечні дефолтні налаштування
- HTTPS/TLS конфігурація
- CORS налаштування

**5. Звіт:**
Склади список знайдених проблем із пріоритетом (Critical/High/Medium/Low) та рекомендованим виправленням.

Якщо $ARGUMENTS — конкретний файл або директорія — фокусуйся тільки на ній.
Якщо $ARGUMENTS порожній — аудит всього проекту.
```

**Використання:**

```
/security-audit
/security-audit src/api/auth
/security-audit src/api/payments
```

## Розширені патерни кастомних команд

### Команди з умовною логікою

```markdown
---
description: "Розгортання в середовище"
---

Розгорни проект у середовище: $ARGUMENTS

Якщо $ARGUMENTS = "staging":
- Використовуй .env.staging
- Не чіпай production дані
- Запусти smoke тести після деплою

Якщо $ARGUMENTS = "production":
- Спочатку покажи diff відносно поточного production
- Вимагай явного підтвердження "YES" перед деплоєм
- Зроби backup даних
- Задокументуй деплой у DEPLOYS.md
```

### Команди для конкретних фреймворків

Зберігайте команди, специфічні для вашого стеку, в проектному `.claude/commands/`:

```
.claude/commands/
├── new-component.md      # Scaffold нового React компоненту
├── new-api-route.md      # Новий Next.js API route з валідацією
├── add-test.md           # Тест для поточного файлу
├── explain-error.md      # Пояснення помилки з логів
└── optimize-query.md     # Оптимізація SQL-запиту
```

### Передача складних аргументів

```markdown
Проаналізуй продуктивність: $ARGUMENTS

Очікуваний формат аргументу: "файл:функція" або просто "файл"
Приклад: /profile src/api/search.ts:searchProducts
```

## Команди в команді vs. глобальні

**Проектні команди** (`.claude/commands/`):
- Специфічні для технологічного стеку проекту
- Відомі всій команді, комітяться в репозиторій
- Приклади: `/new-component`, `/db-migrate`, `/pr-description`

**Глобальні команди** (`~/.claude/commands/`):
- Особисті workflow-команди незалежно від проекту
- Не комітяться, лише для поточного розробника
- Приклади: `/daily-standup`, `/explain-code`, `/review-with-checklist`

При конфлікті імен проектна команда має пріоритет над глобальною.
