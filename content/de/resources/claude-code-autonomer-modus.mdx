# Claude Code im autonomen Modus: --print, CI/CD und Batch-Verarbeitung

Claude Code ist primär als interaktives Tool konzipiert — du tippst, es antwortet, du überprüfst und bestätigst. Aber es hat auch einen vollwertigen nicht-interaktiven Modus für Automatisierung: CI/CD-Pipelines, geplante Jobs, Batch-Verarbeitungsskripte und die Integration in größere automatisierte Workflows.

Dieser Leitfaden behandelt alles, was du benötigst, um Claude Code zuverlässig headless auszuführen.

---

## Das --print Flag: Nicht-interaktiver Output

Das zentrale Flag für Automatisierung ist `--print` (Kurzform: `-p`). Es weist Claude Code an, deine Eingabe zu verarbeiten, die Antwort auf stdout auszugeben und zu beenden — keine interaktive Session, keine Bestätigungsabfragen, kein Warten.

```bash
claude --print "Fasse die Änderungen der letzten 5 Commits zusammen"
```

```bash
# Kurzform
claude -p "Was macht die main-Funktion in src/index.ts?"
```

**Was --print verändert:**

Im interaktiven Modus hält Claude Code eine Session aufrecht, fragt vor Tool-Calls um Bestätigung und wartet auf deine Eingabe. Mit `--print`:
- Verarbeitet Claude Code den Prompt, führt erforderliche Tool-Calls aus und gibt die finale Antwort aus
- Beendet sich mit Exit-Code `0` bei Erfolg, ungleich null bei Fehler
- Output geht nach stdout; Fehler nach stderr
- Keine interaktiven Bestätigungsabfragen — Tool-Call-Genehmigungen werden über die `--allowedTools`-Konfiguration gesteuert

**Output-Format:**

Standardmäßig gibt `--print` Claudes Antwort als Klartext aus. Für strukturierten Output in Skripten kannst du JSON-formatierte Antworten in deinem Prompt anfordern, wobei der Output trotzdem der Rohtext ist, den Claude produziert (kein strukturierter JSON-Wrapper von Claude Code selbst).

## stdin-Piping an Claude Code

Du kannst Inhalte direkt in Claude Code pipen — essenziell für die Verarbeitung von Dateien, Logs oder Befehlsoutput:

```bash
# Datei zur Analyse pipen
cat src/auth/session.ts | claude --print "Überprüfe diese Datei auf Sicherheitsprobleme"

# Git-Diff für eine Commit-Nachricht pipen
git diff --staged | claude --print "Schreibe eine prägnante Commit-Nachricht für diese Änderungen"

# Fehler-Logs zur Diagnose pipen
cat logs/error.log | claude --print "Identifiziere die Grundursache dieser Fehler und schlage Fixes vor"

# Test-Output pipen
npm test 2>&1 | claude --print "Die Tests schlugen fehl. Identifiziere welche Tests fehlschlugen und warum basierend auf diesem Output"
```

Beim Pipen wird der stdin-Inhalt dem Prompt vorangestellt. Claude Code liest sowohl den gepipten Inhalt als auch deinen Prompt-Text gemeinsam.

**Gepipten Input mit Dateikontext kombinieren:**

Claude Code hat auch im `--print`-Modus noch Zugang zum Dateisystem. Du kannst also ein bestimmtes Inhaltsstück pipen, und Claude liest bei Bedarf auch verwandte Dateien:

```bash
git diff --staged | claude --print "Schreibe eine Commit-Nachricht. Prüfe auch CLAUDE.md auf unsere Commit-Nachrichten-Konventionen und halte dich daran."
```

## --allowedTools und --disallowedTools

Im nicht-interaktiven Modus muss Claude Code wissen, welche Tools es ohne Rückfrage verwenden darf. Die Flags `--allowedTools` und `--disallowedTools` steuern dies.

### --allowedTools

Gibt eine Whitelist von Tools an, die Claude verwenden darf. Tools, die nicht in der Liste stehen, werden blockiert.

```bash
# Nur Leseoperationen erlauben — keine Schreibvorgänge, keine Shell-Ausführung
claude --print --allowedTools "Read,Glob,Grep" "Analysiere die Codebase-Struktur und identifiziere zirkuläre Abhängigkeiten"

# Lesen und Schreiben erlauben, aber keine Shell-Ausführung
claude --print --allowedTools "Read,Write,Edit,Glob,Grep" "Refaktoriere das Authentication-Modul"

# Alles außer Bash erlauben (nur Lesen/Schreiben)
claude --print --allowedTools "Read,Write,Edit,MultiEdit,Glob,Grep,LS" "Alle veralteten API-Aufrufe aktualisieren"
```

**Verfügbare Tool-Namen:**

| Tool | Funktion |
|------|----------|
| `Read` | Dateiinhalte lesen |
| `Write` | Dateien schreiben/erstellen |
| `Edit` | Bestehende Dateien bearbeiten |
| `MultiEdit` | Mehrere Bearbeitungen in einer Operation |
| `Bash` | Shell-Befehle ausführen |
| `Glob` | Dateien nach Mustern suchen |
| `Grep` | Dateiinhalte durchsuchen |
| `LS` | Verzeichnisinhalte auflisten |
| `TodoRead` | Aufgabenliste lesen |
| `TodoWrite` | Aufgabenliste aktualisieren |

### --disallowedTools

Gibt zu blockierende Tools an. Alles, was nicht in dieser Liste steht, ist erlaubt (vorbehaltlich deiner Einstellungen).

```bash
# Nur Shell-Ausführung blockieren — alle Lese-/Schreiboperationen erlauben
claude --print --disallowedTools "Bash" "Alle TypeScript-Typfehler überprüfen und beheben"

# Schreiboperationen blockieren — Nur-Lese-Modus
claude --print --disallowedTools "Write,Edit,MultiEdit,Bash" "Sicherheitslücken in der Codebase analysieren"
```

### Wahl zwischen --allowedTools und --disallowedTools

**Verwende --allowedTools wenn:** du strikte Kontrolle möchtest und nur einem bestimmten Satz von Operationen vertraust. Dies ist die sicherere Wahl für nicht vertrauenswürdigen Code oder produktionsnahe Automatisierung.

**Verwende --disallowedTools wenn:** du eine oder zwei gefährliche Operationen blockieren und alles andere erlauben möchtest. Nützlich, wenn du Claude die meisten Operationen vertraust, aber spezifische Risiken verhindern willst (wie Shell-Ausführung in einer Code-Review-Pipeline).

## --dangerously-skip-permissions: Wann sicher, wann nicht

Für CI/CD-Umgebungen, in denen Claude Code ohne jegliche Bestätigungsabfragen operieren soll, kombiniere `--dangerously-skip-permissions` mit Tool-Einschränkungen:

```bash
claude --print \
  --dangerously-skip-permissions \
  --allowedTools "Read,Write,Edit,Glob,Grep" \
  "Alle veralteten API-Aufrufe auf die neuen v2-Endpunkte migrieren"
```

### Wann --dangerously-skip-permissions sicher ist

Das Flag ist sicher in folgenden Szenarien:

- **Kurzlebige CI-Container:** Der Container existiert nur für diesen Job und wird danach verworfen. Kein dauerhafter Schaden möglich.
- **Isolierte Test-Umgebungen:** Claude Code läuft in einer Sandbox ohne Zugang zu Produktionssystemen, echten Datenbanken oder sensiblen Credentials.
- **Read-only-Aufgaben mit explizitem `--allowedTools`:** Wenn du ausschließlich Leseoperationen erlaubst, entfällt das Schadensrisiko fast vollständig.
- **Versionierte Repositories:** Alle Dateiänderungen sind in Git rückverfolgbar. Fehler können zurückgesetzt werden.

### Wann --dangerously-skip-permissions gefährlich ist

Das Flag ist **nicht sicher** in diesen Szenarien:

- **Direkte Produktionszugang:** Wenn der CI-Job Zugang zu Produktionsdatenbanken, Cloud-Credentials oder Live-Infrastruktur hat
- **Ohne --allowedTools:** Niemals `--dangerously-skip-permissions` allein in der Automatisierung verwenden — immer genau angeben, welche Tools Claude verwenden darf
- **In Containern mit gemounteten Secrets:** Wenn der Container `.env`-Dateien, SSH-Keys oder Cloud-Credentials enthält
- **Auf nicht-vertrauenswürdigem Code:** Wenn Claude Code ein Repository analysiert, dessen Inhalte du nicht kontrollierst

**Kritische Sicherheitsregeln für --dangerously-skip-permissions in CI:**

1. **Immer mit --allowedTools kombinieren.** Niemals `--dangerously-skip-permissions` allein in der Automatisierung verwenden.
2. **Niemals in Containern mit Produktionszugang ausführen.** CI-Jobs mit diesem Flag sollten in kurzlebigen Containern ohne Zugang zu Produktionsdatenbanken, Credentials oder Infrastruktur laufen.
3. **Claude Code-Version pinnen.** In CI eine gepinnte Version verwenden: `npm install -g @anthropic-ai/claude-code@1.x.x` für konsistentes Verhalten.
4. **Wo möglich Read-only-Dateisystem-Mounts verwenden.** Quellverzeichnisse als Read-only mounten, wenn der Task keine Dateien schreiben muss.

## GitHub Actions Workflow: Automatisches PR-Review

```yaml
# .github/workflows/claude-review.yml
name: Claude Code Review

on:
  pull_request:
    types: [opened, synchronize]

jobs:
  review:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pull-requests: write

    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0  # Vollständige History für Diff-Kontext

      - name: Node.js einrichten
        uses: actions/setup-node@v4
        with:
          node-version: '20'

      - name: Claude Code installieren
        run: npm install -g @anthropic-ai/claude-code

      - name: PR-Diff abrufen
        id: diff
        run: |
          git diff origin/${{ github.base_ref }}...HEAD > /tmp/pr.diff
          echo "diff_size=$(wc -c < /tmp/pr.diff)" >> $GITHUB_OUTPUT

      - name: Claude Code Review ausführen
        id: claude_review
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: |
          REVIEW=$(cat /tmp/pr.diff | claude --print \
            --allowedTools "Read,Glob,Grep" \
            "Überprüfe diesen Pull-Request-Diff. Fokussiere auf: Bugs, Sicherheitsprobleme, fehlende Fehlerbehandlung und Code-Qualität. Formatiere als prägnanter GitHub PR Review-Kommentar mit Markdown.")
          
          echo "review<<EOF" >> $GITHUB_OUTPUT
          echo "$REVIEW" >> $GITHUB_OUTPUT
          echo "EOF" >> $GITHUB_OUTPUT

      - name: Review-Kommentar posten
        uses: actions/github-script@v7
        with:
          script: |
            github.rest.issues.createComment({
              issue_number: context.issue.number,
              owner: context.repo.owner,
              repo: context.repo.repo,
              body: `## Claude Code Review\n\n${{ steps.claude_review.outputs.review }}`
            })
```

**Automatisierte Test-Generierung bei Push:**

```yaml
# .github/workflows/claude-tests.yml
name: Fehlende Tests generieren

on:
  push:
    branches: [feature/*, fix/*]

jobs:
  generate-tests:
    runs-on: ubuntu-latest
    if: contains(github.event.head_commit.message, '[gen-tests]')

    steps:
      - uses: actions/checkout@v4

      - name: Node.js einrichten
        uses: actions/setup-node@v4
        with:
          node-version: '20'

      - name: Abhängigkeiten installieren
        run: npm ci

      - name: Claude Code installieren
        run: npm install -g @anthropic-ai/claude-code

      - name: Tests für geänderte Dateien generieren
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: |
          CHANGED_FILES=$(git diff HEAD~1 --name-only --diff-filter=AM | grep -E '\.(ts|tsx|js|jsx)$' | grep -v '\.test\.' | grep -v '\.spec\.')
          
          for file in $CHANGED_FILES; do
            if [ -f "$file" ]; then
              claude --print \
                --allowedTools "Read,Write,Glob,Grep" \
                "Schreibe Unit-Tests für $file. Folge den bestehenden Test-Mustern im Projekt. Erstelle die Test-Datei im entsprechenden __tests__-Verzeichnis oder neben der Quelldatei."
            fi
          done

      - name: Generierte Tests committen
        run: |
          git config --global user.name "Claude Code Bot"
          git config --global user.email "claude@ci.local"
          git add "**/*.test.*" "**/*.spec.*" 2>/dev/null || true
          git diff --staged --quiet || git commit -m "chore: generierte Tests hinzugefügt [skip ci]"
          git push
```

## GitLab CI Äquivalent

```yaml
# .gitlab-ci.yml (relevanter Job)
claude-review:
  stage: review
  image: node:20
  before_script:
    - npm install -g @anthropic-ai/claude-code
  script:
    - git fetch origin $CI_MERGE_REQUEST_TARGET_BRANCH_NAME
    - git diff origin/$CI_MERGE_REQUEST_TARGET_BRANCH_NAME...HEAD > /tmp/mr.diff
    - |
      REVIEW=$(cat /tmp/mr.diff | claude --print \
        --allowedTools "Read,Glob,Grep" \
        "Überprüfe diesen Merge-Request-Diff. Identifiziere Bugs, Sicherheitsprobleme und Code-Qualitätsprobleme. Output als Markdown.")
      echo "$REVIEW" > review-output.md
  artifacts:
    paths:
      - review-output.md
    expire_in: 1 week
  only:
    - merge_requests
  variables:
    ANTHROPIC_API_KEY: $ANTHROPIC_API_KEY  # In GitLab CI/CD-Variablen setzen
```

## Batch-Shell-Skript 1: JSDoc-Kommentare hinzufügen

Dieses Skript verarbeitet alle JavaScript-Dateien in einem Verzeichnis und fügt JSDoc-Kommentare zu undokumentierten Funktionen hinzu:

```bash
#!/bin/bash
# jsdoc-hinzufuegen.sh — JSDoc-Kommentare zu allen undokumentierten Funktionen hinzufügen

set -euo pipefail

SRC_DIR="${1:-src}"
PROCESSED=0
SKIPPED=0

echo "JSDoc-Verarbeitung gestartet für: $SRC_DIR"
echo "================================================"

find "$SRC_DIR" -name "*.js" -not -name "*.test.js" -not -name "*.spec.js" | sort | while read -r file; do
  echo "Verarbeite: $file"
  
  # Prüfen ob Datei Funktionen ohne JSDoc hat
  FUNCTIONS=$(grep -c 'function\|=>\s*{' "$file" 2>/dev/null || echo "0")
  EXISTING_JSDOC=$(grep -c '/\*\*' "$file" 2>/dev/null || echo "0")
  
  if [ "$FUNCTIONS" -gt "$EXISTING_JSDOC" ]; then
    claude --print \
      --allowedTools "Read,Write" \
      "Füge JSDoc-Kommentare zu allen exportierten Funktionen und Klassen in $file hinzu, die noch keine haben. Bewahre den gesamten bestehenden Code und alle Kommentare exakt. Füge nur @param, @returns und eine kurze Beschreibung hinzu."
    
    PROCESSED=$((PROCESSED + 1))
    echo "  Fertig: $file"
  else
    SKIPPED=$((SKIPPED + 1))
    echo "  Übersprungen (bereits dokumentiert): $file"
  fi
  
  # Rate-Limiting — Claude Code API hat Ratenlimits
  sleep 2
done

echo "================================================"
echo "Batch-Verarbeitung abgeschlossen."
echo "Verarbeitet: $PROCESSED Dateien"
echo "Übersprungen: $SKIPPED Dateien"
```

**Verwendung:**

```bash
chmod +x jsdoc-hinzufuegen.sh
./jsdoc-hinzufuegen.sh src/
./jsdoc-hinzufuegen.sh lib/utils/
```

## Batch-Shell-Skript 2: Changelog generieren

Dieses Skript generiert einen strukturierten Changelog aus Git-Commit-History:

```bash
#!/bin/bash
# changelog-generieren.sh — Strukturierten Changelog aus Git-History generieren

set -euo pipefail

VERSION="${1:-}"
FROM_TAG="${2:-}"
TO_TAG="${3:-HEAD}"
OUTPUT_FILE="CHANGELOG.md"

if [ -z "$VERSION" ]; then
  echo "Verwendung: $0 <version> [from-tag] [to-tag]"
  echo "Beispiel: $0 v2.1.0 v2.0.0 HEAD"
  exit 1
fi

echo "Changelog für $VERSION wird generiert..."

# Git-Log für den Bereich abrufen
if [ -n "$FROM_TAG" ]; then
  GIT_LOG=$(git log "$FROM_TAG".."$TO_TAG" --pretty=format:"%h %s (%an, %ad)" --date=short 2>/dev/null)
else
  GIT_LOG=$(git log --pretty=format:"%h %s (%an, %ad)" --date=short --since="30 days ago" 2>/dev/null)
fi

if [ -z "$GIT_LOG" ]; then
  echo "Keine Commits im angegebenen Bereich gefunden."
  exit 0
fi

# Bestehenden Changelog lesen wenn vorhanden
EXISTING_CHANGELOG=""
if [ -f "$OUTPUT_FILE" ]; then
  EXISTING_CHANGELOG=$(cat "$OUTPUT_FILE")
fi

# Changelog-Eintrag durch Claude generieren lassen
CHANGELOG_ENTRY=$(echo "$GIT_LOG" | claude --print \
  --allowedTools "Read" \
  "Generiere einen strukturierten Changelog-Eintrag für Version $VERSION aus diesen Git-Commits.

Formatiere als:
## [$VERSION] - $(date +%Y-%m-%d)

### Neue Features
- ...

### Fehlerbehebungen
- ...

### Verbesserungen
- ...

### Breaking Changes (falls vorhanden)
- ...

Gruppiere verwandte Commits. Schreibe auf Deutsch. Fasse triviale Commits (Tippfehler, Minor Fixes) zusammen. Ignoriere CI/chore-Commits außer sie sind bedeutsam.")

# Temporäre Datei für neuen Changelog erstellen
TEMP_FILE=$(mktemp)

echo "$CHANGELOG_ENTRY" > "$TEMP_FILE"

if [ -n "$EXISTING_CHANGELOG" ]; then
  echo "" >> "$TEMP_FILE"
  echo "---" >> "$TEMP_FILE"
  echo "" >> "$TEMP_FILE"
  echo "$EXISTING_CHANGELOG" >> "$TEMP_FILE"
fi

mv "$TEMP_FILE" "$OUTPUT_FILE"

echo "Changelog erfolgreich generiert: $OUTPUT_FILE"
echo "Version: $VERSION"
echo "Commits verarbeitet: $(echo "$GIT_LOG" | wc -l)"
```

**Verwendung:**

```bash
chmod +x changelog-generieren.sh

# Vollständigen Changelog seit letztem Tag generieren
./changelog-generieren.sh v2.1.0 v2.0.0

# Changelog für letzten Monat generieren
./changelog-generieren.sh v2.1.0

# In CI/CD-Pipeline verwenden
./changelog-generieren.sh "${NEW_VERSION}" "${PREVIOUS_TAG}" HEAD
```

## Strukturierter JSON-Output

Claudes `--print`-Output ist Klartext. Für die Integration mit anderen Tools musst du entweder den Text parsen oder Claude anweisen, in einem bestimmten Format auszugeben.

**Strukturierten Output anfordern:**

```bash
ANALYSE=$(claude --print \
  --allowedTools "Read,Glob,Grep" \
  "Analysiere die Codebase auf TODO-Kommentare. Gib NUR valides JSON in genau diesem Format aus:
{
  \"anzahl\": <Zahl>,
  \"eintraege\": [
    {\"datei\": \"<Pfad>\", \"zeile\": <Zahl>, \"text\": \"<TODO-Text>\"}
  ]
}
Gib nichts anderes aus — nur das JSON-Objekt.")

# Mit jq parsen
echo "$ANALYSE" | jq '.anzahl'
echo "$ANALYSE" | jq '.eintraege[] | select(.datei | contains("auth"))'
```

**Exit-Code-Behandlung in Skripten:**

```bash
claude --print --allowedTools "Read,Glob,Grep" "Prüfe ob TypeScript-Fehler in src/ vorhanden sind"
EXIT_CODE=$?

if [ $EXIT_CODE -ne 0 ]; then
  echo "Claude Code ist auf einen Fehler gestoßen"
  exit 1
fi
```

**Mehrstufige Pipeline:**

```bash
#!/bin/bash
# analyse-pipeline.sh — Mehrstufige Code-Analyse

# Schritt 1: Sicherheitsprobleme identifizieren
echo "Schritt 1: Sicherheitsanalyse..."
SICHERHEIT=$(claude --print \
  --allowedTools "Read,Glob,Grep" \
  "Identifiziere die drei kritischsten Sicherheitsprobleme in src/. Gib NUR JSON aus: {\"probleme\": [{\"schwere\": \"kritisch|hoch|mittel\", \"datei\": \"...\", \"beschreibung\": \"...\"}]}")

# Schritt 2: Nur kritische Probleme beheben
KRITISCHE=$(echo "$SICHERHEIT" | jq -r '.probleme[] | select(.schwere == "kritisch") | .datei')

if [ -n "$KRITISCHE" ]; then
  echo "Schritt 2: Kritische Probleme beheben..."
  for datei in $KRITISCHE; do
    claude --print \
      --allowedTools "Read,Write,Edit" \
      "Behebe das kritische Sicherheitsproblem in $datei. Erkläre die Änderung in einem Kommentar."
    sleep 2
  done
fi

echo "Pipeline abgeschlossen."
```

## Wann autonomer Modus, wann interaktiv?

### Autonomer Modus ist richtig für:

| Anwendungsfall | Empfohlene Flags |
|---------------|-----------------|
| PR-Review in CI | `--print --allowedTools "Read,Glob,Grep"` |
| Auto-Formatierung nach Merge | `--print --allowedTools "Read,Write,Edit"` |
| Security-Audit über mehrere Repos | `--print --allowedTools "Read,Glob,Grep"` |
| JSDoc/Kommentare in Batch hinzufügen | `--print --allowedTools "Read,Write"` |
| Commit-Nachrichten generieren | `--print --allowedTools "Read"` (mit stdin) |
| Changelog-Generierung | `--print --allowedTools "Read,Write"` |
| Geplante Code-Health-Reports | `--print --dangerously-skip-permissions --allowedTools "Read,Glob,Grep"` |

### Interaktiver Modus bleibt besser für:

- Komplexes Refactoring mit architektonischen Entscheidungen
- Neue Features entwickeln, die Anforderungs-Klärung brauchen
- Debugging mit unbekannter Ursache
- Jede Aufgabe, bei der menschliches Urteilsvermögen im Prozess erforderlich ist
- Arbeiten in Produktionsumgebungen, wo unbeaufsichtigte Änderungen zu Risiken führen

## Häufige Fehler und Debugging

**Claude Code hängt in CI:**

```bash
# Timeout hinzufügen
timeout 300 claude --print --allowedTools "Read,Glob,Grep" "Analysiere src/"
```

**Rate-Limit-Fehler bei Batch-Verarbeitung:**

```bash
# Verzögerungen zwischen Aufrufen einbauen
for file in $FILES; do
  claude --print --allowedTools "Read,Write" "Verarbeite $file"
  sleep 3  # 3 Sekunden zwischen Aufrufen
done
```

**Output-Encoding-Probleme:**

```bash
# UTF-8-Encoding erzwingen
LANG=de_DE.UTF-8 claude --print "Analysiere..."
```

**Großes Repository — Kontext-Limit:**

```bash
# Codebase auf relevante Dateien einschränken
find src/auth -name "*.ts" | xargs -I{} claude --print \
  --allowedTools "Read" \
  "Überprüfe {} auf Sicherheitsprobleme"
```

## Fazit

Claude Codes autonomer Modus verwandelt eine interaktive KI-Entwicklungsumgebung in ein leistungsstarkes CI/CD-Werkzeug. Das `--print`-Flag, kombiniert mit `--allowedTools` und dem richtigen Verständnis von `--dangerously-skip-permissions`, gibt dir präzise Kontrolle darüber, was Claude in automatisierten Umgebungen tun darf.

Der Schlüssel liegt in der Sicherheitsschichtung: Tool-Beschränkungen zuerst, kurzlebige Container zweites, und `--dangerously-skip-permissions` nur dort, wo die Umgebung wirklich isoliert ist. Mit diesen Grundsätzen lässt sich Claude Code sicher in jede Build-Pipeline, jeden Deployment-Workflow und jede Batch-Verarbeitungsaufgabe integrieren.
